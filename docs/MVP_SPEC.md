# Bid Agent MVP 产品定义

## 1. 产品目标

Bid Agent 帮助咨询人员把招标文件中的技术要求和评分点，转成可追溯、可编辑、可导出的技术方案章节。

MVP 只验证一条最短闭环：

> 新建项目 → 上传招标文件 → 自动提取要求 → 人工确认 → 生成一个章节 → 人工编辑 → 导出 Word

不把“一次生成整本投标文件”、复杂多智能体协作、企业知识库运营和自动投标承诺纳入 MVP。

## 2. 用户与核心场景

主要用户是负责技术标编制的咨询人员。

用户需要：

1. 为一次投标建立独立项目。
2. 上传 PDF 或 DOCX 招标文件。
3. 查看系统提取的技术要求、评分点及原文出处。
4. 修改、删除或确认要求。
5. 选择一组已确认要求，生成一个技术方案章节。
6. 在网页中修改章节内容。
7. 导出包含来源说明的 DOCX 文件。

## 3. 简化业务流程

| 步骤 | 用户动作 | 系统结果 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 新建项目 | 保存项目名称和状态 | 项目可再次打开 |
| 2 | 上传文件 | 保存原文件并启动解析 | 文件状态变为“解析完成”或明确失败 |
| 3 | 检查要求 | 展示分类、原文、页码和置信度 | 用户能回看原文出处 |
| 4 | 确认要求 | 编辑、删除、确认提取结果 | 至少一条要求已确认 |
| 5 | 生成章节 | 输入章节标题并选择要求 | 生成内容与要求建立关联 |
| 6 | 编辑章节 | 人工修改并保存 | 最新版本持久化 |
| 7 | 导出 Word | 点击导出并下载 | DOCX 可正常打开 |

## 4. MVP 功能范围

### 4.1 项目

- 创建、查看项目。
- 展示项目当前阶段和最近更新时间。
- 每个文件、要求、章节和导出物必须属于一个项目。

### 4.2 文件与解析

- 支持 PDF、DOCX。
- 保存原始文件、文件哈希、解析状态和错误信息。
- PDF 按页提取文本，保留真实页码。
- DOCX 按段落提取文本；由于 DOCX 排版会随环境变化，MVP 使用段落序号定位，不伪造页码。
- 空文件、加密文件、损坏文件和不支持类型需要明确报错。
- 扫描 PDF 的 OCR 不进入 MVP，先提示用户上传可检索版本。

### 4.3 要求提取与确认

要求分为：

- 技术要求
- 评分点
- 交付要求
- 资格或约束条件

每条要求至少保存：

- 规范化描述
- 原文摘录
- 来源文件
- PDF 页码或 DOCX 段落范围
- 分类
- 重要程度
- 提取置信度
- 人工确认状态

用户可以编辑、确认和删除。未确认要求不能直接用于最终章节。

### 4.4 单章节生成与编辑

- 用户输入章节标题，并选择已确认要求。
- 系统按“要求 → 写作提示 → 草稿 → 校核结果”生成一个章节。
- 章节必须记录响应了哪些要求。
- 不得虚构案例、资质、参数和产品能力；缺少事实依据时使用明显的待补充标记。
- 支持失败重试，重试不能覆盖用户已保存版本。
- 用户可以编辑和保存正文。

### 4.5 DOCX 导出

- 导出项目名称、章节标题、正文和要求响应清单。
- 文件名可识别且不包含敏感信息。
- 导出记录可重复下载。

## 5. 明确不做

- 一键生成整本技术标。
- 自动生成商务报价。
- 多租户、复杂组织权限和计费。
- 扫描件 OCR。
- 全自动外部资料检索。
- 在没有证据时自动补全企业业绩或资质。
- 复杂 LangGraph 多智能体编排。

## 6. 状态定义

### 项目状态

`draft` → `parsing` → `reviewing_requirements` → `writing` → `ready_to_export` → `exported`

失败不会改变项目主阶段，具体错误记录在文件、任务或导出记录中。

### 文件状态

`uploaded` → `parsing` → `parsed`

失败状态为 `parse_failed`，允许重试。

### 要求状态

`pending` → `confirmed`

用户删除后为 `rejected`，保留审计记录但默认不展示。

### 章节状态

`drafting` → `generated` → `edited` → `approved`

生成失败为 `generation_failed`，允许基于相同输入重试。

## 7. 验收标准

使用一份真实、可检索的招标 PDF 完成以下验收：

1. 能创建项目并在刷新页面后重新打开。
2. 能上传文件，解析状态和错误信息真实可见。
3. 至少提取 5 条候选要求。
4. 每条要求能定位到正确文件和 PDF 页码，原文可核对。
5. 用户能编辑并确认至少 3 条要求。
6. 能基于已确认要求生成一个章节。
7. 章节明确记录其响应的要求，且没有无依据的事实承诺。
8. 用户编辑正文后刷新页面，内容仍然存在。
9. 能导出并打开 DOCX，正文和响应清单完整。
10. 失败操作能看到可理解的原因并可重试。

## 8. 质量与安全底线

- 所有生成内容都必须经过人工确认。
- 所有要求都必须可追溯；无法定位来源的内容不得标记为已确认。
- 原文件、解析结果、中间草稿和用户编辑版本均持久化。
- 密钥只通过运行环境注入，不写入数据库明文、日志、代码或 Git。
- 日志不记录完整招标文件内容和用户上传文件。
